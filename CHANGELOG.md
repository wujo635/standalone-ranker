# Changelog

Full release history for Ranker. See [ARCHITECTURE.md](ARCHITECTURE.md) for the current version numbers, the versioning rules, and how to bump them.

## App version (APP_VERSION)

Follows semantic versioning: `major.minor.patch`

- **major** — breaking change that requires a data migration
- **minor** — new feature, backward compatible
- **patch** — bug fix

| 1.18.0 | Bug fix (real report): a device that had synced more than once could be misclassified as `diverged` relative to an older copy still elsewhere, and confirming that dialog — reasonably read as "sync" — actually discarded the *more advanced* local comparisons in favor of the older file. `relateBaselines()` now checks each side's full `ancestry` chain (every past baseline id, not just the immediate `parentId`), so "ahead by several syncs" is recognized correctly instead of only "ahead by exactly one." The diverged confirm dialog also now shows both sides' revision numbers as a hint. See [ARCHITECTURE.md](ARCHITECTURE.md#merging-rankings-between-devices). |
| 1.18.1 | Bug fix (real report): User A and B both ranked the same items and uploaded in sequence; a subsequent pull silently dropped one side's comparisons. Root cause: `mergeImport()`'s replay branch always rebuilt ratings from `localBase.ratings`, but when incoming's baseline is a more-advanced descendant (established by someone else's earlier merge), that stale snapshot is missing history already "compacted" into `incBase.ratings` — replay now correctly starts from whichever side is actually more advanced. Contributing cause: `uploadToFirestore()` never advanced the local baseline when there was nothing to merge against yet (empty Firestore doc), leaving local `matchLog` inconsistently "unsynced" even after a successful push; new `advanceLocalBaseline()` fixes that too. See [ARCHITECTURE.md](ARCHITECTURE.md#merging-rankings-between-devices). |
| 2.0.0 | **Major rewrite of the sync/merge system.** Three real merge bugs in a row (1.17.1, 1.18.0, 1.18.1) all traced to the same root cause: reconciling two client-side snapshot baselines is inherently fragile. Removed `syncBase`/`ancestry`/`relateBaselines()` entirely — `mergeImport()` is now an unconditional set-union by id (tombstones, then items, then matches), followed by a full replay from scratch via new `replayAllMatches()`. No more confirm dialogs, no more "diverged" case, no more classification step to get wrong. Item deletions are now tracked as permanent tombstone events (`state.itemDeletes`) instead of being silently untracked — a locally-deleted item merging with a device that still has it no longer brings it back. Firestore storage is now a real append-only log (`rankers/shared/items`, `/matches`, `/itemDeletes` subcollections, one doc per fact, doc-ID deduped) instead of a single JSON-blob document — push and pull no longer need to happen in any particular order, and Upload now only pushes what's new (tracked via local per-device cursors) instead of the whole history every time. **Requires updating the Firestore security rules in the Firebase console** to cover the new subcollections — see [ARCHITECTURE.md](ARCHITECTURE.md#cloud-sync-firestore). See [ARCHITECTURE.md](ARCHITECTURE.md#merging-rankings-between-devices) and [ARCHITECTURE.md](ARCHITECTURE.md#item-deletions). |
| 2.0.1 | **Critical bug fix, same-day:** 2.0.0's `mergeImport()` reset every item to `{elo:1000, wins:0, losses:0}` and replayed the full `state.matchLog` from scratch on every merge (`replayAllMatches()`). This silently wiped existing history for anyone upgrading from pre-2.0.0, because `matchLog` was never a device's *complete* lifetime history — the old baseline design compacted it into a snapshot after every sync and cleared it, so an upgraded device's `matchLog` was often only the recent tail, with everything before that already baked into `item.elo`/`wins`/`losses` instead. The first Pull/Upload/Import after upgrading discarded that pre-compacted history. Fixed by replacing `replayAllMatches()` with `applyNewMatches()`, which never resets anything — it filters incoming matches down to ones not already in local `matchLog` and applies only those directly onto whatever ratings are already live, the same way a real vote does. Also fixes a related bug found in follow-up review: `unionItemsAndSchema()` left `elo`/`wins`/`losses` as `undefined` on a brand-new item pulled fresh from Firestore (item docs there never carry ratings by design), turning into `NaN` on its first match — new items now explicitly default to `1000`/`0`/`0`. See [ARCHITECTURE.md](ARCHITECTURE.md#merging-rankings-between-devices). |
| 2.0.2 | **Bug fix found in manual review, before any real data was affected:** importing a full export into an empty/wiped device double-counted every match — a source device's item ratings and its `matchLog` are two views of the same live history, so adopting a brand-new item's rating wholesale *and* replaying its matches from `matchLog` counted each one twice. This is exactly the recovery path for a wiped device, so it needed to be correct before use. Fixed: `unionItemsAndSchema()` now tracks which item ids were just created (`freshlySeeded`); `mergeImport()` excludes any match touching a freshly-seeded item from `applyNewMatches()`, and — since ELO updates are coupled and can't be half-applied — leaves those matches out of local `matchLog` entirely so a later merge can still apply them correctly once the item is no longer fresh (self-correcting, not a permanent gap). See [ARCHITECTURE.md](ARCHITECTURE.md#merging-rankings-between-devices). |
| 2.0.3 | **Bug fix, real report, same-day as 2.0.2:** the 2.0.2 fix above broke Firestore Pull for any brand-new item. It marked every newly-created item as `freshlySeeded` unconditionally, assuming (correctly, for file imports) that the item's incoming rating already reflects its matches — but Firestore item docs never carry ratings at all, so a Firestore-sourced new item always starts at 1000/0/0 with nothing baked in, and 2.0.2 was still excluding its matches from being applied. Those matches were then silently dropped (not deferred — only *applied* matches get added to local `matchLog`), so the item's rating never updated and no error surfaced. Reported live: User A added an item, recorded 10 comparisons, pushed; User B pulled, got the item and a "synced" toast, but no rating changes. Fixed: `unionItemsAndSchema()` now only marks an item `freshlySeeded` when its incoming payload actually carries a rating (`inc.elo !== undefined`) — true for file-import items, false for Firestore items, whose matches are now always applied normally on first pull. See [ARCHITECTURE.md](ARCHITECTURE.md#merging-rankings-between-devices). |
| 2.0.4 | **Bug fix, found in review while discussing Firestore free-tier scaling:** `uploadToFirestore()` put every pending item/match/tombstone write into a single Firestore batch, but Firestore hard-caps a batch at 500 operations — exceeding it fails the entire commit, pushing nothing. Routine day-to-day syncing rarely approaches that, but a large backlog (long time offline, a big CSV import ranked heavily before the first sync, or a from-scratch device recovery uploading its entire lifetime history in one shot) could hit it and silently fail the whole Upload. Fixed: writes are now collected as `[ref, data]` pairs and committed in chunks of at most 500, with the small root-doc merge-write always last; upload cursors only advance once every chunk succeeds, so a mid-upload failure safely retries everything (idempotent, since every doc is keyed by its own fact's id) rather than losing progress. Also documented (no code change): a device's first Pull reads its entire lifetime match history at once, bounded by Firestore's 50k-reads/day free-tier quota — a non-issue at this app's intended scale, but a direct consequence of the never-compact append-only design worth having on record. See [ARCHITECTURE.md](ARCHITECTURE.md#cloud-sync-firestore). |
| 2.1.0 | **New feature:** items can share a title within a category if distinguished by another field, flagged `identity: true` in the Schema Editor (e.g. Year for Movies — two "Dune" entries from different years no longer collide). Previously `itemKey(cat, title)` hashed only category + title, forcing a workaround of baking disambiguating info into the title itself, and worse: `bulkAddCSVImport()` matched existing items by title alone and *silently overwrote* the existing item's fields on a "duplicate" — a real report confirmed a CSV import for "Dune" (2021) destroyed an existing "Dune" (1984) entry's data. `itemKey()` now takes an optional identity suffix (`identitySuffixFor()`/`identitySuffixForFields()`), built from whichever fields are flagged identity; every id-computing call site (`addItem`, `saveItem`, `bulkAddCSVImport`, `applyCSVImport`) now goes through it, so there's one canonical notion of "same item" everywhere. Marking a field identity forces it required (avoids weak disambiguation from a blank value). Toggling identity flags for an existing category triggers a bulk rekey in `saveSchema()` (via new `remapItemIds()`, same remap shape as the v4 migration that introduced `itemKey()`) — blocked outright, with no data changed, if it would merge two distinct existing items. Purely additive: a category with no identity fields hashes identically to before, no `DATA_SCHEMA_VERSION` bump needed. Known limitation, by deliberate choice: schema field edits (including identity flags) don't sync between devices — both users need to flag the same field independently, same as any other schema edit today. See [ARCHITECTURE.md](ARCHITECTURE.md#item-identity-fields-210). |
| 2.2.0 | **New feature, fixing a real incident:** items can now be undeleted, so they can sync again after being removed. Deterministic item ids (`(cat, title, identity field values)` — see 2.1.0) plus an unconditional, permanent tombstone meant deleting an item and later recreating one with the exact same title + identity value(s) computed to the same id, which was then permanently blocked from ever syncing again on any device that had seen the delete — happened live with two "Superman" entries during identity-field cleanup, requiring manual Firestore + console intervention that wasn't repeatable once the affected device became unreachable. Fixed with a parallel `state.itemUndeletes` log, same shape and treatment as `itemDeletes`; new `latestPerItemId()` reduces either log to one entry per item (max `ts`), and `currentlyTombstonedIds()` resolves an item as tombstoned iff its latest delete is newer than its latest undelete (ties favor deleted — `undeleteItem()` guarantees its own `ts` is always strictly after the delete it targets, so a user's own immediate undelete can't lose a same-millisecond tie). New "Deleted items" section in the Data tab lists current tombstones with an Undelete button; undeleting does **not** restore the item's old rating/history, only clears the sync block going forward. Cloud sync (`uploadToFirestore()`/`pullFromFirestore()`) mirrors the existing `itemDeletes` plumbing exactly, including a new `lastUploadedUndeletesAt` cursor. Purely additive: no `DATA_SCHEMA_VERSION` bump, no migration — reduces safely to "one entry per item" on each log without needing per-event unique ids. Requires updating Firestore security rules to add the new `itemUndeletes` subcollection. See [ARCHITECTURE.md](ARCHITECTURE.md#item-deletions). |
| 2.2.1 | **Bug fix, real report, same-day as 2.2.0:** `uploadToFirestore()` crashed with "Cloud sync error" on any tombstone created before `title`/`cat` existed on `itemDeletes` — real pre-2.2.0 tombstones have no `title`/`cat` at all, so the write payload's `t.title`/`t.cat` were genuinely `undefined`, and Firestore's SDK rejects `undefined` field values outright (a client-side throw before the write is even sent: `Unsupported field value: undefined`). Hit live: undeleting a pre-2.2.0 tombstone, then Upload. Fixed by falling back to `null` (`t.title ?? null`, `t.cat ?? null`) in both the `itemDeletes` and `itemUndeletes` write payloads. See [ARCHITECTURE.md](ARCHITECTURE.md#item-deletions). |
| 2.3.0 | **Bug fix, real report:** a fresh import/pull of a full baseline into a wiped device didn't carry over the source device's identity field flags. Root cause: schema was only ever adopted from an incoming payload for a category the receiving device had *zero* schema for — but built-in categories (Movies, etc.) always have a default schema from `CAT_DEFAULTS` the moment the app loads, so even a freshly-cleared device already "has a schema," and the old `if (!state.schema[c])` check silently skipped adopting anything from the incoming side, identity flags included. Fixed: `unionItemsAndSchema()` now calls new `adoptIncomingIdentityFields()` for categories it already knows — monotonically adopts any field the incoming side has flagged `identity: true` that the local side hasn't (never removes one; that's the collision-risk direction the interactive Schema Editor check exists to guard). Adopting a flag on an existing category needs the same rekey-with-collision-check `saveSchema()` already does interactively, so that logic was extracted into shared `rekeyItemsForIdentityFields()` rather than duplicated. Schema and item ids are never committed out of sync with each other — if the rekey would collide (only realistic with pre-existing corrupted data), the adoption is skipped for that category this merge rather than left half-applied. `required`/`filterable` and non-identity field edits remain local-only, unchanged. See [ARCHITECTURE.md](ARCHITECTURE.md#item-identity-fields-210). |
| 2.4.0 | **Bug fix, real report:** editing an item's title (or an identity field's value) left a duplicate on other devices — both the old- and new-titled entries — after the next sync. Root cause: `saveItem()`'s single-item rekey never told any other device the old id was stale; the old id's Firestore doc was simply left in place untouched, so a device that already had a copy under the old id kept it forever while the new id arrived as a separate item. Fixed: the rekey branch now pushes a tombstone for the old id, exactly like `deleteItem()` already does — `mergeImport()`'s existing tombstone handling then retires the stale copy on any device that pulls it, reusing already-tested infrastructure rather than inventing a new sync mechanism. Reintroduces the tombstone-blocks-recreation tradeoff (renaming something back to a prior title/identity-value hits the same trap as any delete) but that trap now has a real fix — Undelete (2.2.0) — so the cost is much lower than it would have been before that existed. See [ARCHITECTURE.md](ARCHITECTURE.md#merging-rankings-between-devices). |
| 2.4.1 | **Internal refactor (no behavior change):** the filter UI (`buildFilterFieldCards()`, `buildFilterPanel()`, `renderFilterUI()`) was the one place in the app still built entirely from hand-written inline `style="..."` strings instead of the CSS classes/custom-properties every other view uses — moved those styles into new `.filter-*` classes in `<style>`, and extracted the field-name-plus-"Has value"-checkbox header that both the number and categorical field-card branches were duplicating into a shared `filterCardHeader()`. Verified visually in-browser (light and dark) for both card types, plus checkbox/pill interaction, before and after. |
| 2.4.2 | **Bug fix, found during the 2.4.1 refactor's review:** `inferFieldType()`'s per-field type cache (`fieldTypeCache`) was never invalidated, so whatever verdict it computed the very first time a field was checked — including "string" from sampling zero items, before any data existed yet — stuck forever. A genuinely numeric field like Year could get permanently stuck rendering the categorical pill-filter instead of the min/max/exact grid, even once real numeric data existed, because nothing ever cleared the stale entry. Fixed with new `invalidateFieldTypeCache(cat)`, called from every place a category's item fields can change: `addItem()`, `saveItem()`, `deleteItem()`, the CSV import paths (bulk add / replace / create, all funneled through `resolveCSVImport()`), and `mergeImport()`/`clearAllData()` (which clear the whole cache, since those can touch any number of categories at once and aren't hot paths like the search-box keyup that originally motivated caching at all). Verified in-browser: reproduced the stale-cache staying wrong after adding numeric data, then confirmed each fix path clears it correctly. |
| 2.5.0 | **New feature/bug fix, found during review of the sync/merge model:** deleting a category never told other devices — `confirmDeleteCat()` already tombstoned its items individually (via `deleteItemsInCat()`), so those correctly vanished everywhere, but the category name/schema itself had no tombstone anywhere, and `unionItemsAndSchema()`'s cats/schema merge is purely additive (union only ever adds, never removes). Any device that already had the category kept it forever — now empty, but still selectable, still with its full field schema — since nothing ever told it the category itself was gone. Category *creation* already worked fine (purely additive, same union logic new items use). Fixed with new `state.catDeletes`/`state.catUndeletes` tombstone logs, same shape and "latest ts per key wins" resolution as `itemDeletes`/`itemUndeletes` (generalized the shared reduction into `latestByKey()`/`currentlyTombstonedKeys()`, with `latestPerItemId()`/`currentlyTombstonedIds()` and new `latestPerCat()`/`currentlyTombstonedCats()` as thin wrappers). `mergeImport()` purges a newly-tombstoned category's name/schema/items before unioning in — needed even though items are already individually tombstoned, since a concurrent edit on another device (e.g. adding a new item to that category before learning it was deleted) has no such tombstone of its own, and could otherwise resurrect the whole "deleted" category via that one item. Unlike item undelete, there's no dedicated "Undelete category" button: `saveNewCat()` just unconditionally pushes a `catUndeletes` fact for whatever name it creates, so a (re)created category name always just works and syncs — there's no data to consciously restore either way, since deletion already permanently wipes a category's schema and items via the existing item-tombstone path. Cloud sync mirrors `itemDeletes`/`itemUndeletes` exactly: new `catDeletes`/`catUndeletes` Firestore subcollections (keyed by new `catKey(cat)`, a hash — a raw category name isn't guaranteed to be a valid Firestore doc id), their own upload cursors, requires updating Firestore security rules for the two new subcollections. Purely additive, same as `itemUndeletes` in 2.2.0: no `DATA_SCHEMA_VERSION` bump. Verified via simulated multi-device merges (creation propagates; deletion propagates including cats/schema/items; recreating a deleted category's name isn't permanently blocked; a concurrent new item in a since-deleted category doesn't resurrect it) and through the real `saveNewCat()`/`confirmDeleteCat()` UI functions directly. | 2.5.1 | **Bug fix, found during review of the sync/merge model (same review as 2.5.0):** adding a brand-new field to an existing category and filling it in on an item silently never showed up on other devices. Root cause: `unionItemsAndSchema()`'s schema merge for a category the device already knows about only ever adopted fields flagged `identity: true` (2.3.0) — an ordinary new field was never added at all. | 2.5.2 | **Critical bug fix, real report:** pulling into a device whose identity flags for a category were behind another's duplicated *every item in that category*. Root cause: `unionItemsAndSchema()` unioned incoming items *before* adopting incoming schema — but adopting a newly-synced identity flag rekeys every existing local item in that category onto a new id scheme (`adoptIncomingFields()` → `rekeyItemsForIdentityFields()`). Unioning items first, against ids still computed under the device's *old* scheme, meant incoming items (computed under the sender's *newer* scheme) never matched any local item and got added as "new" duplicates right alongside the originals — unconditionally, for every item in the category, not an edge case. Hit live: after finally regaining Firestore Pull access (see 2.5.0/2.5.1's rules-update requirement), the very next pull duplicated the entire Library. Fixed by reordering `unionItemsAndSchema()` to adopt schema/identity fields first, so local items are already rekeyed onto the incoming scheme by the time items are compared — they now correctly merge into one regardless of pull order. This also retires the "flag identity on B before pulling" manual rollout-order workaround documented since 2.1.0 — no longer necessary. Verified: reproduced the exact duplication with a two-device simulation (matching field values on both sides, differing only in whether Year was flagged identity locally), confirmed the fix merges to one item, and re-ran the full 2.5.0/2.5.1 regression suite (category creation/deletion propagation, new-field propagation, identity-collision safety) to confirm the reordering didn't regress anything else. See [ARCHITECTURE.md](ARCHITECTURE.md#item-identity-fields-210). |

Root cause: the 2.0.2 double-counting fix excludes any match touching a `freshlySeeded` item (a brand-new item whose incoming payload already carries a real rating) from being re-applied — correct, since the rating's already baked in — but it also excluded such matches from `state.matchLog` entirely, on the assumption a *later* merge would eventually re-deliver them once the item was no longer fresh. ## Data schema version (DATA_SCHEMA_VERSION)

Incremented only when the shape of `state` changes in a way that requires migration logic.

| Version | Shape |
|---|---|
| 1 | Items had a hardcoded `year` string field. No `schema` object. |
| 2 | `schema` introduced as a plain array of `{name, required}` per category. No `primary` label. |
| 3 | `schema[cat]` is `{ primary: string, fields: [{name, required}] }`. `_meta` block added to exports. |
| 4 | Item ids switched from random `uid()` to deterministic `itemKey(cat, title)`; items gained `updatedAt`. Added `state.matchLog` (append-only pairwise results since the last sync) and `state.syncBase` (`{id, parentId, rev, ts, ratings}` snapshot baseline) to support merging rankings from two devices. History entries gained `matchIds` linking them to the log entries they created. |
| 5 | `syncBase` gains `ancestry` — the full chain of past baseline ids in a lineage, not just the immediate `parentId`. Fixes `relateBaselines()` misclassifying a multi-sync device as `diverged` relative to an older copy (see 1.18.0). |
| 6 | `syncBase` removed entirely. Added `state.itemDeletes` (permanent deletion tombstones) and `state.lastSyncedServerTs` (local Firestore pull cursor). `state.matchLog` changes meaning from "unsynced comparisons since a baseline" to "the full permanent match history" — see 2.0.0. |
